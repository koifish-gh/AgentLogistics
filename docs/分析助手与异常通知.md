# 分析助手与负责人通知

入口：分析助手（/#/assistant）。支持多轮聊天、状态摘要、机器人/订单/故障分析、决策说明、修复指引。每问重新采集快照，标注 tick、采集时间、事件依据。分析不会推进时间、改变事件游标或执行操作。站内异常清单中的修复按钮才会显式执行修复。

复用 agent/llm.mjs 与现有密钥。未配置模型或请求超时，明确标示本地摘要；不假装完成智能推理。历史最近12条，每条最多4000字符；问题最多2000字符；全服务同时最多一个模型问答。模型等待不占仿真修改队列。对话仅存当前页面会话内存，清空或刷新会消失，不保存密钥。

数据范围：最多100个未完成订单、最近80条事件、最近4轮决策；总体数字来自全量 KPI。回答中的事件依据是最近12条快捷索引，不保证每条都与问题相关。事件文本属于数据，机械故障根因没有模拟，禁止从占用热力图推断电池/电机故障。

## 异常通知建议（外部渠道尚未实现）

已有站内故障清单和人工修复入口。要及时通知仓库负责人，建议新增持久告警服务：

1. 接收 robot_faulted 领域事件，使用「世界/重置代次 + sequence」作为幂等键，记录位置、关联订单、发生时间、负责人和建议动作。
2. 告警状态：待通知→已送达→已确认→处理中→已恢复。通知成功不能代替修复成功。robot_repaired 后标记恢复。
3. 通过企业微信/钉钉/飞书 webhook 或邮件发送；后端存储凭据，不放浏览器。接收人、渠道、确认超时由负责人配置。
4. 失败进行有限重试和退避；同一故障不逐 tick 重发；确认超时才提醒/升级。故障被修复再发生应形成新告警。
5. 通知正文采用规则化事实：机器人、坐标、事件时间、影响订单、处理入口。模型可生成附加建议，但不能决定是否发送关键告警。
6. 持久化发件队列，重启续发；记录送达状态。服务暂停/断电时本机无法提供通知，需要常驻设备或独立监控。
7. 拥堵告警需持续时间阈值和冷却；暂无全局吞吐下降基线，不应仅凭累计 KPI 自动报警。

启用前需确定：通知平台、负责人的实际账号、凭据、故障等级、确认期限和升级联系人。当前没有向任何人发送外部消息。
