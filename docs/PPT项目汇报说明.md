# AgentLogistics PPT 项目汇报说明

供 PPT 制作和答辩讲解使用。内容以当前可演示的系统为准。

制作前请先记住三条边界：

- 网页演示中，机器人平时按规则赶路和派单。大模型只在机器人故障、通道对向、订单突发三类事件中被调用。
- 不要写成「每走一格都由大模型控制」，也不要写成「每来一张订单都询问模型」。
- 页面上的 tick、完成单数、路径格数、利用率和热力图来自当次仿真。不要预先填入固定实验结果。后端未连接时的曲线是演示快照，不能当作实验数据。

默认演示：24×16 网格、5 组双深货架、5 台机器人。演示地址：`http://127.0.0.1:8788/`。

# 03 项目背景与问题

- PPT标题：仓库在变化，调度不能只靠固定规则

**本页目的**  
把课程项目收束成一个明确问题，为后文的 Agent 介入做铺垫。

**建议展示的内容**

- 订单会持续进入，也会突然增加一批
- 多台机器人同时执行不同订单，通道狭窄
- 道路可能被封锁，机器人可能故障并停在通道上
- 只按距离分配，难以同时照顾负载和突发变化
- 环境变化后，需要重新分配任务或改写剩余路径

核心问题，单独放大：

> 当仓库环境不断变化时，机器人应该如何调整任务和路径？

**建议使用的项目截图/页面**  
不必先放完整界面。可用四个短句配简单图标：订单、多机器人、封锁、故障。若要配图，用总览里能同时看到多台机器人和路径的局部。

**页面需要强调的重点**  
问题不是「如何画一张仓库图」，而是多机器人在变化环境中如何继续完成任务。

**演讲时可以怎么讲**  
仓储通道窄，多台机器人会迎面相遇，也可能有人封锁道路，或者某台车突然故障。订单还在不断进来。如果每一种情况都写死规则，演示既慢，也说不清为什么这样调度。所以我们要把实时状态放进仿真，并在真正需要判断的时候再做一次决策。

# 04 项目总体思路

- PPT标题：Agent 负责决策，仿真负责执行

**本页目的**  
讲清系统的工作闭环，并主动说明大模型不控制每一步移动。

**建议展示的内容**

一条闭环，不要写成八个同等大小的文字块堆在一起：

环境感知 → 任务理解 → 关键决策 → 任务分配 → 路径执行 → 状态反馈 → 异常出现 → 再次决策

闭环下方用两行对照：

- 平时：空闲机器人遇到待分配订单，按「到目标的格数 + 已完成单数 × 4」分配，不调用模型
- 例外：故障、通道对向、订单突发，才调用对应 Agent；失败时退回同一套规则

**建议使用的项目截图/页面**  
以流程图为主。可在流程末端放一张很小的总览缩略图，表示执行结果能回到地图上被看到。

**页面需要强调的重点**

- Agent 不是聊天窗口，也不遥控机器人每一格怎么走
- 仿真内核保证路径、碰撞和订单状态
- 决策结果要能在地图和决策页上对上

**演讲时可以怎么讲**  
系统先看到仓库里有哪些空闲机器人、哪些订单还没人接、有没有故障和对向。平时用一条公开的代价规则完成分配，机器人沿路径前进。只有故障、两车对向、或者我们主动注入的订单突发，才请模型做一次判断。模型若超时或没有给出有效动作，系统仍按规则继续，演示不会停住。

# 05 系统总体架构

- PPT标题：三层协作：界面、Agent、仿真

**本页目的**  
说明数据怎么走，避免把六个页面误解成六套独立系统。

**建议展示的内容**

三列架构，中间用箭头表示「操作向下、快照向上」。

用户交互层

- 总览与数字孪生
- 机器人管理、订单调度
- Agent 决策与数据分析
- 仿真控制与场景注入

Agent 决策层

- 判断本步是赶路、普通派单，还是关键事件
- 普通派单：本地规则
- 关键事件：异常 Agent、路径 Agent 或派单 Agent
- 决策后请求仿真前进一步

仿真执行层

- 24×16 仓库地图与货架障碍
- 机器人、订单、A* 路径
- 碰撞检查、故障、封锁
- tick、指标与事件日志

**建议使用的项目截图/页面**  
架构图即可。不要把六个页面的截图都贴在这一页。

**页面需要强调的重点**

- 浏览器不直接改仓库，命令由 Agent 转给仿真
- 仿真返回的世界快照，是地图、表格和曲线的共同来源
- 网页演示以这条事件触发链路为准

**演讲时可以怎么讲**  
上面一层负责看和操作，中间一层决定这一步要不要问模型，下面一层把移动、碰撞和订单状态算出来。每推进一步，新的仓库状态回到界面。因此评委在地图上看到的位置、在订单表里看到的状态，和决策页里的说明，来自同一次仿真。

# 06 仓库数字孪生与仿真

- PPT标题：调度发生在一张可运行的仓库里

**本页目的**  
说明数字孪生是调度的观察和执行场景，不是单独的三维展示。

**建议展示的内容**

在总览大图上用标注指出：

- 货架：障碍，不能通行，也不能作为取送货点
- 货架之间的通道
- 机器人：空闲、取货途中、送货途中、故障
- 取货点与送货点
- 按机器人区分的路径
- 地图上方的决策说明

图旁用三句话，不要再介绍按钮：

- 时间按 tick 推进，每步最多移动一格
- 同一时刻不允许重叠、对向交换或跟车进入同一格
- 等距、俯视、侧视只改变观察方式，不改变仓库状态

**建议使用的项目截图/页面**  
总览页「仓储数字孪生」，打开路径和订单点。机器人已经在移动时截图。右侧「运行指标」可保留一条窄边，底部场景事件不必完整展开。

**页面需要强调的重点**  
仓库、机器人、订单和最近一次调度说明出现在同一画面，调度是否生效可以直接看见。

**演讲时可以怎么讲**  
这是默认的 24×16 仓库，五组货架，五台机器人。灰色区域是货架，车只能走通道。每一步全体最多移动一格，并且不能互相撞上或互换位置。地图上的路径和取送货点都对应真实坐标。后面注入故障或封锁时，也是在这张图里看结果。

# 07 Agent 智能决策

- PPT标题：关键时刻，由 Agent 做出可解释的选择

**本页目的**  
这是重点页。讲清 Agent 何时出现、依据什么选择，以及页面上哪些信息是算出来的。

**建议展示的内容**

左侧放决策过程，右侧放三类 Agent，不要画成一个永远在线的对话机器人。

一次可见的决策：

获取当前机器人与订单 → 计算到目标的格数和已完成单数 → 比较候选代价 → 选定机器人或改写路径 → 仿真执行 → 写入决策说明

三类才会调用模型的情况：

| 事件 | Agent | 实际动作 |
| --- | --- | --- |
| 机器人故障 | 异常 Agent | 把未完成订单改派给其他空闲机器人，故障车保持停机 |
| 通道对向 | 路径 Agent | 只让剩余路程更长的一台避开对面那一格 |
| 订单突发 | 派单 Agent | 把这批新订单分散给不同空闲机器人 |

代价单独写出：

> 代价 = 到目标的格数 + 已完成单数 × 4

补充一句：候选对比由当前坐标和完成单数算出，不是模型内部的隐藏分数。普通待分配订单走这套规则，不调用模型。

**建议使用的项目截图/页面**  
Agent 决策页。优先包含：顶部四步、调度简图、候选对比、决策原因或决策说明。需要先运行并完成至少一次分配、让路或故障改派，再截图。空页面不要使用。

**页面需要强调的重点**

- Agent 参与的是任务选择和路径调整，不是聊天
- 选择依据可以在页面上核对
- 顶栏变红时，表示某个 Agent 正在询问模型

**演讲时可以怎么讲**  
决策页会列出每台机器人到目标还有多少格、已经完成多少单，以及综合代价。少完成任务的机器人，可以优先于单纯距离更近的机器人。平时新订单按这个规则分配。只有故障、对向和我们注入的订单突发，才会请对应的 Agent 询问模型，并在这里留下原因。模型没有给出有效动作时，系统会写明已经改回规则处理。

# 08 多机器人任务调度

- PPT标题：五台机器人同时执行不同订单

**本页目的**  
说明多机器人如何分工，而不是介绍机器人页面有哪些按钮。

**建议展示的内容**

用一张「订单状态」和一张「机器人状态」对照：

- 订单：待分配 → 已分配 → 运输中 → 已完成
- 机器人：空闲 → 去取货 → 去送货 → 空闲
- 一台机器人同时只执行一张订单
- 不同机器人的路径用不同颜色区分
- 待分配订单可以指定给一台空闲机器人，这一步不经过模型

图下给一个具体关系，用现场真实编号，不要编造：

> 订单 #N 由 Rk 执行，取货点与送货点显示在订单表和地图上，剩余时间等于剩余路径格数。

**建议使用的项目截图/页面**

- 主图：订单调度页，能看到不同状态和分配到的机器人
- 辅图：机器人管理页的列表加俯视简图，或总览中多条彩色路径
- 两张图说明同一件事：多台车在执行不同订单

**页面需要强调的重点**  
调度的结果是「哪张订单交给哪台机器人」，并且这条关系在订单页、机器人页和地图上一致。

**演讲时可以怎么讲**  
五台机器人不会抢同一张订单。一张单只交给一台空闲车，车先去取货点，取到后再去送货点。订单表里能看到它现在是待分配、已分配、运输中还是已完成；机器人页能看到这台车当前站在哪一格、还剩多少路。地图上的颜色则把这些任务同时摊开。

# 09 动态事件与异常恢复

- PPT标题：环境变化之后，系统重新调度

**本页目的**  
这是现场演示的核心页。说明价值在于变化发生后的调整，而不只是顺利送完订单。

**建议展示的内容**

一条演示链：

注入事件 → 仓库状态改变 → 下一步识别事件 → Agent 或规则处理 → 改派或重规划 → 机器人继续执行

只列出已经实现的事件：

- 单点封锁：指定一个可走格子
- 路段封锁：在地图上点起点和终点
- 道路恢复：解除已经封锁的单点或路段
- 机器人故障：停在原地，未完成订单退回，不会自动修复
- 修复故障：必须手动执行
- 订单突发：按数量新增一批订单，并在下一步触发派单 Agent

不要出现电量耗尽、通信中断、货架倒塌等未实现事件。

对向让路单独写清：

> 只调整剩余路程更长的那一台，对面和同向跟随的机器人继续走原路。

**建议使用的项目截图/页面**

- 总览底部「场景事件」
- 注入之后的数字孪生：故障机器人或被封锁的格子要能看见
- 顶栏红色状态，例如「异常 Agent 询问模型」或「路径 Agent 询问模型」
- Agent 决策页中对应的一条决策说明

四张小图按时间排开，比一张静态页面更合适。

**页面需要强调的重点**

- 场景按钮先改变仓库，模型在下一步才被调用
- 故障车不会自己恢复
- 待处理订单变多，本身不等于订单突发；突发必须手动注入

**演讲时可以怎么讲**  
正常运行只能说明规则能送货。我们接着改变环境：可以封住一格或一整段路，也可以让一台机器人故障。故障车会停在原地，它没送完的订单交给其他空闲机器人，而这台车要等我们手动修复。若两台车在通道里对向，系统只改路程更长的那一台。顶栏变红，就是 Agent 正在处理这次变化。

# 10 系统功能与界面

- PPT标题：六个页面组成一条调度闭环

**本页目的**  
用一页交代界面范围，避免后面变成逐页功能说明书。

**建议展示的内容**

六个页面各一句：

- 总览：观察全仓，并注入场景、控制仿真
- 机器人管理：核对一台机器人的位置、任务和路径
- 订单调度：核对一张订单的状态，并可手动分配
- Agent 决策：查看候选代价、决策原因和记录
- 数据分析：汇总这一次运行的完成情况与热力
- 系统设置：调整种子、策略、速度和显示；应用仿真参数会重置世界

页面之间用四个动作串起来，而不是六个孤立图标：

观察全仓 → 核对车和订单 → 查看决策原因 → 回看本次结果

**建议使用的项目截图/页面**  
六个页面各一张小图，总览略大。设置页不要超过其他页面的面积。

**页面需要强调的重点**  
这些页面读取同一次仿真。设置页是参数入口，不是第六个业务子系统。页首标语不是四个独立系统。

**演讲时可以怎么讲**  
总览用来看全仓和制造变化，机器人和订单页用来核对某一台车、某一张单，决策页解释为什么这样分，数据分析把这次运行收束成完成率、用时和热力。六个页面不是六项孤立功能，而是同一条调度过程的不同观察角度。

# 11 数据分析与运行效果

- PPT标题：一次仿真运行留下的结果

**本页目的**  
说明系统能回看这次运行，同时避免把仿真指标说成真实仓储实验。

**建议展示的内容**

只使用数据分析页已有指标：

- 完成订单、订单完成率
- 平均完成时间，单位是 tick
- 全队机器人利用率：有任务时间占已运行 tick 的比例
- 当前故障与累计故障次数
- 分机器人的利用率曲线
- 仓库占用热力图：每个格子被停留的 tick，货架不着色
- 订单状态分布
- 平均取货时间、平均送达时间、累计行驶格数、累计等待 tick
- 异常统计：机器人故障、道路封锁、道路恢复、订单突发

页面角落固定标注：

> 数据来自本次仿真，不是真实仓库的历史业务数据。

不要加入订单类型排行、销售额、客户分布，也不要写死「完成率达到百分之多少」。

**建议使用的项目截图/页面**  
数据分析页。热力图和完成订单卡片要清晰。若顶部出现「后端未连接」的警告，这张图不能用于答辩。

**页面需要强调的重点**

- 热力图表示机器人在哪些格子停留得更久
- 订单突发次数等于界面里成功注入的次数
- 指标用于观察这次调度，不用于证明策略全局最优

**演讲时可以怎么讲**  
运行一段时间后，这里能看到完成了多少单、平均用了多少 tick、机器人有多少时间在执行任务，以及哪些通道停留更久。故障、封锁和订单突发也有各自的累计次数。这些都是这次仿真算出来的，用来检查调度过程，而不是一组预先准备的业务报表。

# 12 项目特色与创新点

- PPT标题：围绕动态调度形成的六个特点

**本页目的**  
把已经实现的能力收成答辩中的特色，每一点都能在系统里指出来。

**建议展示的内容**

1. Agent 参与关键决策：故障改派、对向让路、订单突发分配；平时不调用模型
2. 多机器人协同：五台机器人各执行一张订单，并避免同格、对向交换和跟车冲突
3. 数字孪生仓库：24×16 地图、货架、路径和取送货点使用同一套坐标
4. 动态事件可注入：单点封锁、路段封锁、道路恢复、故障、修复、订单突发
5. 异常后的调整：故障订单改派，对向时只重规划路程更长的一台
6. 决策与执行可视：候选代价、决策说明、地图路径和运行指标来自同一次仿真

每一条下面只放一个可以点击到的位置，例如「总览场景事件」「Agent 决策页」。

**建议使用的项目截图/页面**  
不必新截图。用前几页已经出现的总览、决策页和数据分析页做三枚小图，分别对应「看得见」「说得清」「核得对」。

**页面需要强调的重点**  
特色是「变化发生后仍能调度，并且能解释」，不是功能数量。

**演讲时可以怎么讲**  
这个项目的特点不是页面多，而是把决策限制在真正需要判断的时刻，并把结果放回仓库里检查。机器人为什么改道、订单交给了谁、通道哪里更拥堵，都可以在同一次运行中对上。

# 13 应用价值与发展方向

- PPT标题：当前能用于方案验证，尚未连接真实仓库

**本页目的**  
说明课程项目的应用意义，并把未实现内容明确放到未来。

**建议展示的内容**

当前价值

- 观察多机器人在同一仓库中的任务分配
- 在仿真中测试封锁、故障和订单突发
- 用完成时间、利用率、等待和热力图比较一次运行的结果
- 让调度原因可以被讲解和复核

未来可扩展，必须单独成组，并写明「当前未实现」

- 接入真实仓储订单和地图
- 增加更复杂的协同策略，并做策略对比实验
- 扩展更多异常场景
- 与真实机器人或仓储设备连接

不要把以上任何一项写成已有功能。也不要承诺电量、充电或机械臂。

**建议使用的项目截图/页面**  
可以不截图。左侧「当前能做」，右侧「以后可扩展」，用颜色分开。

**页面需要强调的重点**  
它现在是可复现的调度仿真与演示平台，不是生产级仓储控制系统。

**演讲时可以怎么讲**  
当前它适合用来验证调度想法：同样的仓库里，订单如何分配，道路被封或机器人故障后系统如何调整，结果能否在图上和指标里看出来。它还没有接入真实仓库和真实设备。更复杂的策略实验和设备连接，是后续可以扩展的方向。

# 14 总结

- PPT标题：感知、决策、执行，再根据变化重新决策

**本页目的**  
用一条闭环结束，并回到封面标语。

**建议展示的内容**

一行组合：

数字孪生 + Agent 决策 + 多机器人调度 + 动态仿真

一条闭环：

环境感知 → 任务理解 → 智能决策 → 协同执行 → 异常反馈 → 再次决策

底部重复标语：

感知仓库 · 理解任务 · 智能决策 · 协同执行

可加一句收束：

> 平时按规则执行，关键变化由 Agent 决策，结果回到仿真中接受检查。

**建议使用的项目截图/页面**  
总览数字孪生做浅背景或小图。文字保持少。

**页面需要强调的重点**  
结束在闭环，不新增功能点。

**演讲时可以怎么讲**  
AgentLogistics 把仓库状态、机器人调度和关键决策放在同一个仿真里。环境没有特殊变化时，系统按可解释的规则执行；出现故障、对向或订单突发时，Agent 介入一次，并让新的任务或路径继续跑起来。这也是「感知仓库、理解任务、智能决策、协同执行」在这个项目中的具体含义。

# 现场演示建议

这一节不单独做成炫技页，供汇报人控制现场顺序。演示围绕一张订单的生命周期，不逐个点完所有菜单。

建议故事：

订单进入 → 机器人接单并执行 → 环境发生变化 → Agent 重新决策 → 任务继续 → 回看本次结果

推荐操作：

1. 打开总览，开始运行。顶栏为「运行中」，此时不要声称正在调用模型。
2. 注入「订单突发」，指定少量订单。等待顶栏出现红色的「派单 Agent 询问模型」。
3. 打开 Agent 决策页，指出候选代价和这条决策说明，再回到地图看新任务。
4. 注入一台机器人故障，或封锁一段当前有车经过的路。故障不会自动消失。
5. 指出异常 Agent 或路径 Agent 的状态，以及地图上的停机、改派或绕行。
6. 如需恢复，再手动执行「修复故障」或「道路恢复」。
7. 最后打开数据分析，用完成单数、利用率和热力图收尾，并说明这是本次仿真数据。

演示中不要点击「重置世界」或设置页的「应用仿真参数」，二者都会清空当前运行。

若模型超时或额度不足，页面会说明已改用本地规则。此时改为讲解规则如何接住这次事件，不要假装模型已经完成决策。
